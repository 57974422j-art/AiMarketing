# 三套成片状态机拆分方案（2026-09-21）

> 用户指令：「**现在开始三套分开**」「**不要设计公用层** —— 最怕设计了共用，不如不拆，出问题都不能用」
> 并重申既有路线：「**状态机直接执行，不是再把复杂文字给 AI 去分析**」（原因：AI 分析那套"帮做视频"容易出错）

---

## 0. 为什么拆（真因，不是"感觉乱"）

2026-09-21 的事故给出了最直接的证据：

```
AI 模式的改动（vfSrcAI / _vdCur）被塞进了【素材合成也走的共用函数】make_ai_video
→ 那函数里一行变量写错 → 抛异常 → 被 catch 吞掉
→ 素材合成、AI 生成【两条路一起断】（用户点了确认毫无反应）
```

**→ 问题不是"两个状态机混用"，而是"两条线共用了同一段可执行代码"。共用越多，连累越狠。**

---

## 1. 铁律（三条，写进代码注释）

1. **三套之间【不许互相 import】**（除类型声明文件，见 §5）。
2. **不设"共用逻辑层"** —— 宁可重复，也不要"改一处影响三处"。
   重复是**可见**的（改 3 个文件时你会看到）；共用坏掉是**不可见**的（你还以为它好着）。
3. **`route.ts` 只留一件事：判"哪条线"，然后整轮交给那套状态机。**
   不在这里做素材/文案/分镜/计费的任何判断。

---

## 2. 目录与归属（**每套自带全部逻辑**）

```
src/lib/agent/vf/
├── vf-material.ts     ← 【素材合成】完整状态机（自带下列全部）
├── vf-aivideo.ts      ← 【全部 AI 生成】完整状态机（自带下列全部）
├── vf-mix.ts          ← 【素材 + AI 混合】（本期只放"未实现"提示，占位）
└── vf-types.ts        ← 【只放 type/interface，零运行逻辑】（见 §5 的争议说明）
```

**每套 `vf-*.ts` 自带（各自一份，互不引用）**：

| 归属 | 内容 |
|---|---|
| **入口判定** | 这套线自己的入口词正则（如素材合成认「素材合成/用我的素材库」；AI 认「全部AI生成/纯AI」） |
| **草稿** | 自己的内存 Map（`VF_DRAFT_MATERIAL` / `VF_DRAFT_AI`）+ 自己的 DB tag（`vf_draft_mat` / `vf_draft_ai`）+ 自己的 `save/load/clear` |
| **取素材** | 素材合成：查仓库 + 摘要 + 探测尺寸 + 画幅 + 画布；**AI：也查（用户定案"看了素材让它自己决定"，但只当依据，不入片）** |
| **文案** | 自己写文案（字数按 `时长 × 4.5`） |
| **分镜** | 自己排分镜。**AI 那套额外要求 `prompt`（英文画面描述）**；素材合成那套不提这个要求 |
| **确认卡** | 自己出卡。**AI 那套的成本按【秒 × 50】**；素材合成按【字数 ÷ 20】 |
| **门禁** | 自己判覆盖率/镜数/是否有分镜（AI 那套也照素材合成一样的门禁） |
| **出片调用** | 自己拼 `make_ai_video` 的入参（**各自显式传 `source`，不再让对方读草稿去猜**） |
| **日志** | 自己的前缀（`[VF-M]` 素材 / `[VF-A]` AI），日志里能直接看出是哪条线 |

## 3. `route.ts` 只留什么（**薄分派，约 10~15 行**）

```ts
// 成片入口：只判"哪条线"，整轮交给那套状态机（确定性执行，不给 AI 分析）
import * as vfMaterial from '@/lib/agent/vf/vf-material'
import * as vfAivideo  from '@/lib/agent/vf/vf-aivideo'
import * as vfMix      from '@/lib/agent/vf/vf-mix'

const line = vfMaterial.matches(userMessage) ? 'material'
           : vfAivideo.matches(userMessage)  ? 'ai'
           : vfMix.matches(userMessage)      ? 'mix'
           : vfMaterial.hasDraft(uid) ? 'material'      // 已有草稿 → 继续那条线
           : vfAivideo.hasDraft(uid)  ? 'ai'
           : ''
if (line === 'material') { finalResult = await vfMaterial.handle(ctx); return }
if (line === 'ai')       { finalResult = await vfAivideo.handle(ctx);  return }
if (line === 'mix')      { finalResult = await vfMix.handle(ctx);      return }
// line === '' → 落到原来的 AI 自由发挥路径（不进任何状态机）
```

**`ctx` 里只传"原始材料"**（`userMessage` / `auth` / `messages` / `spoke` 等），**不传任何"已算好的中间结果"**。

---

## 4. ⚠️ 这条依赖关系必须一起修（否则拆完还是"崩了没线索"）

**现状**：`route.ts` 里有个 `catch (eVF)` **把状态机异常吞掉**（只写一行 `console.error`）→ 用户端**只看到上一步的旧文案**（这次就是这样：露出「发布流程未开始」）。

**拆分【治不了这个】**。所以必须同时做：
- 状态机抛异常 → **写 `vf_debug.log`** + **给用户端一句人话**（"出片环节出错：<原因>；请把这句发我"）
- **三套各自包一层**，异常绝不静默

---

## 5. 关于 `vf-types.ts`（**请你定**）

- **要它**：只放 `interface`/`type`（**零运行逻辑**）→ 改它**不会让某条线行为变坏**，只是类型。
- **不要它**：三套**各自定义**自己的类型 → **绝对隔离**，代价是类型写 3 遍。

**我倾向：不要它**（贴合你"不要共用"的原则）。**你定。**

---

## 6. ⚠️ Python 层（`make.py` / `render.py` / `tts.py`）**建议不拆**，理由如下

**这三套脚本【本来就已经是"数据驱动"的】**：差别只在每镜的 `type`：

| 镜头来源 | `shots[].type` | 数据 |
|---|---|---|
| 素材合成 | `bgimage` | `src` = 素材图路径 |
| AI 生成 | `aivideo` | `src` = AI 片段路径 |

**→ 渲染/配音/字幕/混音/BGM 是【同一套物理流程】，拆开等于维护 3 份渲染器（更危险）。**

**边界铁律（保护"不拆"的安全）**：**状态机只能通过 `--source` / `plan` 这两个【参数】影响脚本，绝不允许出现"脚本里判断是哪条线"的分支。**

## 7. 实施步骤（**每步可验证，不许一次全改**）

| 步 | 做什么 | 验证方式 |
|---|---|---|
| **1** | **先修 §4 的异常可见**（不拆也算数） | 故意让某处抛异常 → 用户端应看到"出片环节出错：…" |
| **2** | **抽 `vf-material.ts`**（只搬代码，**不改行为**；`route.ts` 改成调它） | 跑一条**素材合成**，行为与拆分前**逐项一致**（确认卡/报价/日志） |
| **3** | 部署 + **你实测一条素材合成** | 出片正常 |
| **4** | **抽 `vf-aivideo.ts`**（把 AI 分支从素材那套里摘出去） | 跑素材合成**仍正常**（证明隔离生效）+ 文档/自检核对 |
| **5** | `vf-mix.ts` 占位（未实现提示） | 点「素材+AI 混合」应提示"开发中"，**不影响另两条** |
| **6** | 三套各自独立自检（`selfcheck.sh` 加"三套入口是否都在位"） | 一键确认 |

**⚠️ 关键**：**第 2、4 步都是"只搬不改"** —— 一旦发现"顺手想优化"，就停下记进待办，不在拆分的同时改行为。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 拆分中把行为改了（"搬家顺手修 bug"） | **只搬不改**；发现的问题记入 `ISSUES.md` 待拆分完成后再处理 |
| 三套的"文案/分镜体验"越走越远 | **接受**（用户明确：宁可重复）；但**确认卡话术**保持一致风格 |
| `route.ts` 分派判断写错 → 走错线 | 分派只有 3 行，且**每套自带 `matches()`**；有草稿时必须"继续原线"，不许串线 |
| 拆分期间线上不可用 | **分两步上线**（先素材、后 AI），每步都有"素材合成必回归"的验证 |
| 草稿 tag 撞车 | **三套用不同 tag**（`vf_draft_mat` / `vf_draft_ai`），历史 `vf_draft` 保留兼容读一次 |

---

## 9. 结论

- **方向对**：三套分开，**不设共用逻辑层**（用户的判断正确，且与此前"标准/自由拆分"的成功经验一致）。
- **同时必做**：**异常可见**（否则拆完仍然"崩了没线索"）。
- **Python 层不拆**（本来就是数据驱动），但**用"只允许通过参数影响"的边界铁律保护它**。
- **实施只搬不改，分两步上线，每步以"素材合成必回归"为验收**。
