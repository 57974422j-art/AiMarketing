### 1.2 缺失的关键能力

| # | 缺失项 | 影响 | 严重程度 |
|---|--------|------|---------|
| **L1** | 直播推流/拉流集成 | 当前无法真正开播，命令控制是Mock | 🔴 致命 |
| **L2** | AI 数字人主播（实时驱动） | 数字人只能生成离线口播视频，无法在直播中实时互动 | 🔴 致命 |
| **L3** | 弹幕/评论实时采集+AI回复 | 无法实现"AI场控"，直播中无人值守互动 | 🔴 致命 |
| **L4** | 直播数据实时统计 | 看板数据是假的 | 🟡 重要 |
| **L5** | 话术与数字人联动 | 话术库里的话术不能自动喂给数字人说 | 🟡 重要 |
| **L6** | 商品智能讲解触发 | 观众问商品时自动调取商品介绍并让数字人讲解 | 🟡 重要 |
| **L7** | 多机位/多场景切换 | 专业直播需要主画面+商品特写+PPT切换 | 🟢 锦上添花 |
| **L8** | 录播切片自动分发 | 直播结束后自动剪辑精彩片段分发到各平台 | 🟢 锦上添花 |

### 1.3 一句话判断

> **项目已经具备了直播的"零件"（数字人/TTS/Q1设备/浏览器），但缺少把零件组装成"整机"的编排层。核心缺口是从「离线视频生成」跨越到「实时互动直播」。**

## 二、产品定位：三种直播模式

### 模式 A：AI 数字人直播（全自动无人直播）

```
┌─────────────────────────────────────────────────────┐
│              AI 数字人无人直播                        │
│                                                     │
│  适用对象：中小商家 / 个体户 / 日不落直播间            │
│  核心价值：7×24小时开播，无需真人出镜                  │
│                                                     │
│  ┌─────────┐    TTS实时合成     ┌──────────┐        │
│  │ AI 对话  │ ──→ 语音流 ─────→ │ 数字人驱动  │        │
│  │ 引擎     │                   │ (唇形同步) │        │
│  └────┬────┘                   └─────┬─────┘        │
│       │                               │              │
│       │  弹幕/评论                    │  视频帧        │
│       ↓                               ↓              │
│  ┌─────────┐                   ┌──────────┐         │
│  │ 实时弹幕  │                   │ OBS/推流   │         │
│  │ 采集引擎  │←── 观众互动 ────→│ 编码器    │         │
│  └─────────┘                   └─────┬─────┘         │
│                                       │               │
│                                  推流到平台             │
│                                  (抖音/快手/视频号)      │
│                                                     │
│  技术方案：                                          │
│  · 数字人用预训练形象 + 实时TTS驱动唇形                 │
│  · 背景可以是静态图/视频循环/绿幕合成                   │
│  · 弹幕通过 Q1 设备或浏览器抓取                         │
│  · AI 根据弹幕关键词匹配话术库或 RAG 生成回复            │
└─────────────────────────────────────────────────────┘
```

**技术选型对比（数字人实时驱动）：**

| 方案 | 延迟 | 效果 | 成本 | 推荐场景 |
|------|------|------|------|---------|
| **预渲染视频 + 切换** | 低(~1s) | 机械 | 低 | 日不落直播（轮播录好的内容） |
| **TTS + 音频驱动唇形(Audio2Face)** | 中(2-5s) | 自然 | 中 | 交互式AI主播 |
| **实时LLM生成 + TTS + 数字人** | 高(5-10s) | 最自然 | 高 | 高客单价直播 |
| **真人半身出镜 + AI辅助** | 极低(<1s) | 最佳 | 需真人 | 大主播/品牌直播 |

**推荐起步方案：TTS + Audio2Face（中等延迟，效果自然，成本可控）**

### 3.2 核心组件详解

#### 组件1: 弹幕采集引擎 (CommentCollector)

```
职责: 从各平台实时获取直播间弹幕和评论

支持的数据源:
┌─────────────┬──────────────────┬──────────────────────┐
│ 来源        │ 采集方式          │ 实现方式               │
├─────────────┼──────────────────┼──────────────────────┤
│ 抖音直播    │ 指纹浏览器DOM轮询  │ Playwright 定时抓取   │
│             │                  │ .webcast-chatroom 元素 │
├─────────────┼──────────────────┼──────────────────────┤
│ 抖音直播    │ Q1设备UIAutomator │ dump + 解析通知栏/弹幕 │
│             │ (手机开播场景)    │ 或截屏OCR识别          │
├─────────────┼──────────────────┼──────────────────────┤
│ 快手直播    │ 指纹浏览器DOM     │ 同抖音策略             │
├─────────────┼──────────────────┼──────────────────────┤
│ 视频号      │ 微信开发者API     │ 需申请直播插件权限      │
└─────────────┴──────────────────┴──────────────────────┘

输出格式:
{
  platform: "douyin",
  userId: "u_88812345",
  userName: "小明",
  avatar: "https://...",
  content: "这个多少钱？",
  timestamp: 1717743600000,
  type: "comment",        // comment/gift/follow/share
  sentiment: "positive",   // positive/negative/neutral (可选AI分析)
  intent: "product_price", // product_price/size/shipping/...
  replied: false
}
```

#### 组件2: AI 对话引擎 (LiveChatEngine)

```
职责: 决定如何回应每条弹幕

决策流程:

  新弹幕进入
     ↓
  [预处理] 敏感词过滤 + 去重 + 黑名单检查
     ↓
  [意图识别] LLM 分类 → intent + 提取实体
     ↓
  ┌───────────────────────────────────────┐
  │           匹配优先级                    │
  ├───────────────────────────────────────┤
  │ 1. 话术库精确匹配 (triggerKeyword)     │
  │    例: "多少钱" → 读取对应商品价格话术   │
  │                                       │
  │ 2. 商品知识库匹配                       │
  │    例: "有红色的吗?" → 商品属性查询      │
  │                                       │
  │ 3. FAQ / 培训文档(RAG)                 │
  │    例: "什么时候发货?" → 文档检索回复    │
  │                                       │
  │ 4. LLM 自由生成 (兜底)                  │
  │    用 Agent 的 promptTemplate 生成      │
  │                                       │
  │ 5. 忽略 (广告/无关/恶意)                │
  └───────────────────────────────────────┘
     ↓
  [风控检查] 同一用户频率限制 + 全局速率限制
     ↓
  [输出] 回复文本 → 送入 TTS → 送入数字人或弹幕回复
```

#### 组件3: 数字人驱动引擎 (DigitalHumanDriver)

```
两种运行模式:

═══ 模式A: 离线预生成（日不落直播）═══

  话术列表 (提前准备)
     ↓
  批量调用 TTS → 音频文件队列
     ↓
  批量调用 digitalHumanVideo() → 视频文件队列
     ↓
  FFmpeg 拼接 + 背景合成 → 长视频
     ↓
  OBS 循环播放 + 插入随机片段避免重复检测
     
  优点: 稳定、延迟极低、不会卡顿
  缺点: 无法实时互动（但可以定期插入"感谢xxx的礼物"等）

═══ 模式B: 实时驱动（交互式AI主播）═══

  AI 生成回复文本
     ↓
  textToSpeech() → 音频流 (火山TTS流式 ~200ms首包)
     ↓
  [Audio2Face] 音频 → 唇形/表情参数 (需额外服务)
     ↓
  数字人渲染引擎 → 视频帧流
     ↓
  OBS 虚拟摄像头输入 → 推流

  技术方案选择:
  ┌────────────────┬───────┬──────────┬──────────────┐
  │ 方案            │ 延迟  │ 成本     │ 推荐阶段       │
  ├────────────────┼───────┼──────────┼──────────────┤
  │ SadTalker开源    │ ~300ms│ 免费(GPU)│ MVP快速验证   │
  │ (本地部署)       │       │          │              │
  ├────────────────┼───────┼──────────┼──────────────┤
  │ 百炼千寻实时数字人 │ ~1s   │ ¥0.5/次  │ 生产环境      │
  │ (API调用)        │       │          │              │
  ├────────────────┼───────┼──────────┼──────────────┤
  │ 即刻数字人API    │ ~800ms│ ¥0.3/次  │ 备选方案      │
  ├────────────────┼───────┼──────────┼──────────────┤
  │ DeepBrain AI    │ ~500ms│ $0.05/次 │ 海外客户      │
  └────────────────┴───────┴──────────┴──────────────┘
     
  推荐: 
  · MVP阶段 → SadTalker 本地部署 (免费但有GPU要求)
  · 正式商用 → 百炼千寻实时API (已有接入)
```

#### 组件4: 推流管理 (StreamManager)

```
职责: 管理直播间的推流生命周期

功能:
  · 开播前检查 (网络/码率/服务器状态)
  · 推流启动/停止/重启
  · 流媒体服务器管理 (SRS/NodeMediaServer)
  · 断线重连 + 画质自适应
  · 多平台同时推流 (抖音+快手)
  · 录制存储 (用于回放和切片)

推荐推流架构:
  
  ┌─────────┐   RTMP   ┌──────────┐   RTMP   ┌──────────┐
  │ OBS/FFmpeg ─────→ │ SRS服务器  ─────→ │ 抖音直播   │
  │ (编码源)  │        │ (中转节点) │        │ 推流地址   │
  └─────────┘        └────┬─────┘        └──────────┘
                          │ RTMP
                          ↓
                    ┌──────────┐
                    │ 快手直播   │
                    │ 推流地址   │
                    └──────────┘

  SRS 的作用:
  · 一路推流源 → 多平台分发
  · 转码 (不同平台不同码率需求)
  · 录制 (FLV → MP4)
  · 断流告警 + 自动重推
```

## 四、与数字人的深度结合设计

### 4.1 数字人在直播中的角色矩阵

| 角色 | 说明 | 使用方式 | 适合场景 |
|------|------|---------|---------|
| **AI 主播** | 数字人作为唯一出镜者 | 全程数字人 + TTS驱动 | 日不落/深夜场 |
| **AI 助播** | 真人主播旁的虚拟助手 | 画中画/分屏，负责念评论/报价格 | 大促/双11 |
| **AI 导购员** | 讲解特定商品时的演示形象 | 切换到商品讲解画面 | 功能展示/教程类 |

### 7.5.3 路线二：预渲染 + FFmpeg RTMP 直推（当前 MVP 方案）

**核心思路**: 利用 AiMarketing **已有的**数字人/TTS能力离线生成视频素材，
通过 FFmpeg 编码后直接 RTMP 推送到直播平台。

**优势**: 
- ✅ **今天就能跑通** — 所有组件已就绪
- ✅ **零额外依赖** — 不需要 GPU 服务器、不需要 Docker、不需要 Q1
- ✅ **稳定可控** — 预审内容，无实时翻车风险
- ✅ **成本最低** — 只消耗服务器带宽和 CPU

**劣势**:
- ❌ 不是真互动（录播轮播模式）
- ❌ 需要反检测策略避免平台封禁
- ❌ 内容更新需要重新生成视频

#### FFmpeg 推流核心命令

```bash
#!/bin/bash
# live-push.sh — 预渲染视频 RTMP 推流脚本

# === 基础推流（最简版）===
ffmpeg -re -i prepared_live_stream.mp4 \
  -c:v libx264 -preset veryfast -b:v 2500k -maxrate 2695k -buf_size 3369k \
  -r 30 \
  -c:a aac -b:a 128k -ar 44100 \
  -f flv "rtmp://push.douyin.com/live/STREAM_KEY"

# === 进阶版（带叠加层+反检测）===
ffmpeg -re -i main_content.mp4 \
  -i background_music.mp3 \
  -i watermark.png \
  -filter_complex "\
    [0:v]scale=1080:1920,setsar=1,split=2[bg][fg];\
    [2:v]overlay=10:10[wm];\
    [bg][wm]overlay=W-w-10:10[base];\
    [base]tpad=start_mode=clone:start_duration=0.3[video];\
    [video]setpts=PTS*0.995[out]" \        # 0.5% 微变速反检测
  -map "[out]" -map 1:a \
  -c:v libx264 -preset fast -b:v 3000k -g 60 \
  -c:a aac -b:a 128k \
  -f flv "rtmp://push.douyin.com/live/STREAM_KEY"

# === 多平台同时推流版（主+备用）===
ffmpeg -re -i content.mp4 \
  -c:v libx264 -preset fast -b:v 2500k \
  -c:a aac -b:a 128k \
  -f flv "rtmp://push.douyin.com/live/KEY1" \
  -c copy -f flv "rtmp://push.kuaishou.com/live/KEY2"
```

#### 反检测策略（关键！）

| 策略 | 方法 | 目的 |
|------|------|------|
| **内容多样性** | 准备 3-5 小时不重复素材，每次直播随机排列 | 避免 MD5/帧指纹检测 |
| **微变速播放** | FFmpeg `setpts=PTS*0.995~1.005` (±0.5%) | 打破固定帧间隔指纹 |
| **BGM 轮换** | 每 15-30 分钟换一首背景音乐 | 增加音频熵值 |
| **插播片段** | 每 8-12 分钟插入感谢/互动/引导视频 | 打破连续播放特征 |
| **画面微调** | 随机轻微缩放/位移 (±2%) | 改变画面布局特征 |
| **真人巡场** | 每 60-90 分钟切入真人画面 2-3 分钟 | 最有效的反检测 |
| **时间模拟** | 模拟真实主播的休息/喝水节奏 | 行为模式接近真人 |
| **多场差异化** | 不同场次使用不同组合的内容包 | 跨场次不重复 |

#### 前置条件

| 条件 | 要求 | 当前状态 |
|------|------|---------|
| **容器镜像** | 必须是 `CQR14-ALL—v1.6.0` | ✅ 已满足 |
| **网络模式** | MacVlan 公有网卡（独立 IP） | ⚠️ 需确认或配软路由 |

#### 优势与局限

| 维度 | 评价 |
|------|------|
| **延迟** | ⭐⭐⭐⭐⭐ WebRTC 级别，极低 |
| **安全性** | ⭐⭐⭐⭐⭐ 通过抖音原生 APP 开播，比裸推 RTMP 安全 |
| **画质保持** | ⭐⭐⭐⭐⭐ OBS 合成质量可控 |
| **部署复杂度** | ⭐⭐ 需要解决网络问题、OBS自动化、Q1联动 |
| **依赖外部** | ⭐⭐ 依赖 Q1 环境 + 软路由 + 魔云腾生态 |
| **文档支持** | ⭐⭐ 官方文档有限，客服一般 |
| **适用场景** | 有 Q1 独立 IP 环境、追求最高安全性的场景 |

#### 适用场景建议

- **适合**: 已有 MacVlan 环境的企业用户、对安全要求极高的场景
- **不适合**: 当前网络环境受限、需要快速落地的阶段
- **定位**: 作为路线一的补充增强（LiveTalking 渲染 → OBS → WHIP → Q1 → 抖音）

## 九、关键技术风险

| 风险 | 影响 | 应对方案 |
|------|------|---------|
| **平台反爬/封禁** | 弹幕采集失效 | 多方案冗余(DOM/UIAutomator/通知栏)；降低采集频率 |
| **数字人实时延迟 > 5s** | 互动体验差 | 先做预渲染模式；实时模式用流式TTS+缓冲 |
| **平台检测无人直播** | 封号风险 | 插入随机互动片段；定期换背景/BGM；真人定时巡场 |
| **GPU资源不足** | 数字人生成慢 | 预渲染可排队；实时模式用云端API |
| **推流不稳定** | 直播卡顿/断流 | SRS断流重连；CDN加速；备用推流线路 |
| **AI回复质量不佳** | 影响品牌形象 | 话术库精确优先；LLM生成仅作兜底；人工审核高频回复 |
