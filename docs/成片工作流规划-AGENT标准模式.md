# 成片工作流规划（AGENT 标准模式 · 纸面方案）

> 日期：2026-09-17 ｜ 状态：**仅规划，未实施** ｜ 作者：AI（与用户讨论定稿）
> 讨论背景：用户看到开源项目 `NanmiCoder/creator-pipeline`（两个 Agent skills：
> `voice-clone-tts` + `web-video-presentation`），问"我们能不能在 AGENT 模式下做一套
> 像『帮我发一个视频』那样的完整自动化"。本文是回答 + 落地方案。
> **用户明确要求：纯生成（不找素材），像博主演示那样画面都是生成的。**

---

## 〇、结论先说（三句话）

1. **按发布状态机的方法走 —— 方向科学，是当前最合适的选择。** 因为标准模式的立身之本就是
   "用户不用会，系统把步骤定死"，状态机正是这个原则的实现。
2. **但不能原样照搬。** 发布是"几秒内选完就发"，成片是"几分钟、多阶段、要花钱"。
   照搬会得到一个跑得动但体验很差的流程。
3. **必须补 3 个发布工作流没有的机制**：异步任务化、成本闸门、单步可重试。
   再补一项从 creator-pipeline 学来的：**衔接校验**（防止"日志说成功、其实是旧结果"）。

---

## 一、为什么"照搬发布状态机"是对的方向

发布工作流的骨架（`src/app/api/agent/chat/route.ts`，注释原文）：

| 设计 | 出处 | 为什么好 |
|---|---|---|
| 任务词命中 → **状态机是唯一路径，绝不 AI 兜底** | L1593 | 流程稳定，不靠模型当次发挥 |
| 状态机词（数字/abc/换/重/确认/选/发）→ **无条件跳过模型** | L1509 | 零延迟、零幻觉 |
| 有草稿 → **跳过 AI 汇总，状态机直接处理** | L1589 | 用户点选项时不会"AI 插嘴" |
| `WF_JSON` 是系统内部协议，**AI 严禁输出** | prompts.ts L76 | 卡片由系统生成，AI 篡改不了 |
| AI 只在"要内容"时出场 | 全流程 | 写标题/话题这种才让模型干 |

**这套结构对成片同样成立**：成片里真正需要"智能"的只有"写文案"和"排分镜"，
其余（选音色、分句 TTS、生成 SRT、合成、转场）全都是**确定性步骤**。

## 二、但不能全照搬：发布 vs 成片的 4 个本质差异

| 维度 | 发布工作流 | 成片工作流 | 由此带来的要求 |
|---|---|---|---|
| **耗时** | 几秒（选完即发） | 几分钟（TTS + 逐段生成 + FFmpeg） | ★ 必须**异步任务化 + 进度反馈** |
| **成本** | ~0（本地脚本） | 每次几毛~几十元（视频生成） | ★ 必须**先报价、用户确认再跑** |
| **失败粒度** | 一次成功/失败 | 8 个阶段，任一可能失败 | ★ 必须**单步可重试**，不从头来 |
| **可回退** | 基本不需要 | 用户常想"改第 3 句再重出" | ★ 草稿要**保存每步产物** |

> **这 4 条就是"骨架照搬、机制新增"的分界线。**

## 三、成片工作流的状态机设计

### 3.1 入口关键词

```
"帮我做一条视频" / "帮我成片" / "帮我做视频" / "AI 成片"
  → 命中即交给 VIDEO 状态机（与发布状态机完全独立，互不干扰）
```

### 3.2 状态与步骤表（核心 · 这就是要反复打磨的东西）

草稿状态：`VIDEO_DRAFT`（结构仿 `PUBLISH_DRAFT`）

| 步 | 名称 | 输入 | 产出 | 谁在做 | 可否回退 |
|---|---|---|---|---|---|
| 1 | **起稿** | 用户一句话主题（或口播稿） | `script.md`（原样保存，不擅自改数字/术语） | 用户 + AI 润色 | ✅ |
| 2 | **选音色** | 音色列表（预置 + 已克隆的） | voice_id | 用户点选 | ✅ |
| 3 | **确认文案** | script.md | 定稿文案 | 用户确认 | ✅ |
| 4 | **分句配音** | 定稿文案 + voice_id | 每句 `tts{i}.mp3` + 各自 duration | 系统（`ttsQwen3`） | ✅ 可只重跑某句 |
| 5 | **出字幕** | 每句音频 + duration | 一条拼合音频 + `SRT` | 系统 | ✅ |
| 6 | **分镜编排** | 文案 + SRT | 分镜表（每镜：画面描述 + 时长 + 转场） | ★ **AI 出场**（写画面描述） | ✅ |
| 7 | **画面生成** | 分镜表 | 每镜画面（**纯生成，不用素材**） | 系统（文/图生视频） | ✅ 可只重跑某镜 |
| 8 | **合成出片** | 画面 + 配音 + SRT | 成品 MP4 | 系统（`smart-compile-engine`） | ✅ |
| 9 | **预览确认** | 成品 | 用户确认 / 重来某步 | 用户 | ✅ |

**★ 关键：AI 只在第 1 步（润色文案）和第 6 步（写画面描述）出场，其余全是确定性步骤。**

### 3.3 卡片协议

复用现有 `WF_JSON`（AI 严禁输出，由状态机生成）。成片需要的卡片类型：

```
· 音色选择卡（预置音色 + 我的克隆音色）
· 文案确认卡（定稿文案 + "改一改"按钮）
· 分镜预览卡（每镜：描述 + 时长 + 缩略图）
· 进度卡（第几步 / 总共几步 / 当前耗时 / 已花费）
· 成品预览卡（播放 + 重新某步 + 导出）
```

### 3.4 AI 出场点（只有 2 处，务必守住）

```
★ 第 1 步：把用户的"一句话/一篇文章"整理成口播文案（保留数字与术语，不改写）
★ 第 6 步：把每句文案变成"画面描述"（给视频生成模型用的提示词）
其余步骤：状态机直接做 —— AI 不许插手（否则就是发布工作流里踩过的"AI 自由回复覆盖状态机"）
```

## 三·补 「素材来源」：双模式 + 混合补足（2026-09-17 用户修正）

用户修正："选素材和生成 **两种模式都要支持**；素材不够的用生成补足。"

**我们天然支持两种**（能力都已有，只差在状态机里加一个选择步）：

| 模式 | 用什么 | 现有能力 |
|---|---|---|
| **A. 用我的素材** | 用户个人仓库（OSS 私有存储）的视频/图片 | `list_personal_files`（带可用 URL） |
| | 平台级素材库（趋势视频/BGM/图片） | `search_storage` |
| **B. 全部生成** | 画面全部由模型生成 | 文生视频 / 图生视频（`generate_video` 等） |
| **C. ★ 混合（推荐）** | 先查素材库 → 有就用、缺的【生成补足】 | A + B 组合 |

**状态机里的落法**：在第 6 步（分镜编排）之后、第 7 步（画面生成）之前插入一步：

```
第 6.5 步 画面来源（卡片让用户选）：
   ○ 全部用我的素材（列出匹配到的素材，让用户确认）
   ○ 全部生成
   ○ 混合：先用素材，缺的自动生成（默认）
处理规则（确定性）：逐镜判断——
   该镜素材库有匹配 → 用素材（记录素材 ID/URL）
   该镜没有匹配   → 标记为"待生成" → 走生成
   每镜在卡片上标明【素材】还是【生成】，用户可逐镜改
```

> 这正好接上我们已有的「诚实协议」（AI 必须先查库再回复、禁编素材）：**有就报有，没有就说没有并建议生成或上传**。

## 三·补2 「它凭什么知道我的项目」—— 每天做宣传片的关键

用户问："AGENT 似乎没有看我项目源码的能力，需要借助什么？"

**查证结果**：

| 能力 | 现状 | 位置 |
|---|---|---|
| **AI 智能体训练文档**（产品介绍/项目说明/行业知识） | ✅ **已有** | `src/app/api/ai-agent/[id]/documents` + 工具 `read_knowledge` |
| 把网站加入知识库 | ✅ 已有 | `add_knowledge_site` / `knowledge-sites` |
| 读项目**源码**仓库 | ❌ **没有** | — |

**建议做法：不读源码，喂"项目说明"**（更稳、更可控）：

```
★ 一次性准备（人做一次）：
   把你的项目介绍写成一份文档（是什么/给谁用/有什么特色/常见卖点/品牌调性），
   传到【AI 智能体训练文档】里 → AGENT 每次成片时用 read_knowledge 读它。
★ 每天使用（用户说一句）：
   "用我的项目资料，做一条今天的宣传片" → 状态机起稿时把项目文档作为输入 → 出片。

★ 为什么不直接喂源码：
   · 源码信息密度太杂（配置/依赖/无关模块），AI 容易抓错重点
   · 每天的宣传片要的是【卖点/调性】，不是【技术实现】
   · 真需要技术亮点时，再补一段"技术特色"到那份文档即可
※ 若将来确实要读代码：需新增"代码仓库接入 + 摘要"能力（二期再议）
```

## 三·补3 「要不要做成 PPT 风格」

博主输出的是**HTML 动态演示**（视觉上像"会动的 PPT"）。

**判断：不必做"真 PPT"，但值得做"PPT 风格模板"。**

```
★ 它选 HTML 的原因：画面完全可控 + 可录屏；代价是要 Node/Vite 环境 + 多一步录屏
★ 我们直接出 MP4 → 更短的路，不需要真做 .pptx，也不需要 HTML 工程
★ ★ 但"动态 PPT"的【视觉语言】值得借鉴：
     卡片式排版、图解释义、连续 MG（动效）、状态变化、文字逐字出现
★ ★ ★ 这些用我们现有的 FFmpeg 链路【能做出近似效果】：
     · 标题样式 ×8（popin/fade/typewriter/glow/outline/gradient/scalePulse/shake）
     · 字幕样式 ×4（普通/卡拉OK/打字机/高亮）
     · 转场 ×8、Ken Burns 运镜 ×7、贴纸
★ 建议形态：做成【几套"风格模板"】而不是让用户调参数
     · 例：科技风 / 商务风 / 清新风 / 促销风
     · 每套 = 一组固定的 视觉规则（配色 + 标题样式 + 转场 + 运镜 + 字号）
     · 用户选一套 → 系统套用到整条片子上（一致性也更好）
```

## 四、必须新增的 3 个机制（发布没有的）

### 4.1 异步任务化 + 进度反馈

```
★ 成片不可能在聊天请求里同步跑完（几分钟）
★ 方案：状态机在第 7 步创建【成片任务】(参考现有 video-task-manager.ts / create_storyboard_task)
        → 前端轮询进度 → 进度以"第 n/9 步 + 百分比 + 已耗时"呈现
★ 复用现有：video-task-manager.ts（视频任务管理）、WF 卡片的进度展示
```

### 4.2 成本闸门（先报价，用户点头再跑）

```
★ 现状：smart-compile-engine.ts 已有 CostEstimate 类型 —— 可复用来算"这条要多少钱"
★ 流程：第 7 步前 → 弹"预计 ¥X，生成吗？" → 用户确认才扣费开跑
★ 为什么必需：视频生成是真金白银，不能"用户说一句就自动烧几十块"
```

### 4.3 单步可重试（不从头来）

```
★ 每步产物落盘 + 记录在 VIDEO_DRAFT 里
★ 第 4 步只重跑第 3 句、第 8 步只重出某镜 → 其余产物直接复用
★ 这是"用户体验"的分水岭：从头跑 5 分钟 vs 只补 20 秒
```

## 五、借鉴 creator-pipeline 的"衔接校验"（缺口补上）

**它做了什么**：`voiceover.json` 存【音频采样帧 + 字幕 + 文件哈希】，
导入下一步时核验；**改稿或缺段后不允许继续拼接旧结果**。

**我们为什么需要**：这正是我们这两天一直在修的病 ——
"日志说成功、其实是空结果/旧结果"（bu:check 谎报成功、抖音封面点空还报成功…）。

**落地方案（低成本、高收益）**：

```
每个阶段产出一个 manifest（清单）：
  · 第 4 步：每句音频的 文件名 + 时长 + hash
  · 第 5 步：拼合音频 hash + SRT hash
  · 第 7 步：每镜画面的 hash
  · 第 8 步：合成前校验 —— 所有引用的产物 hash 必须与清单一致
             不一致 → 明确报错"第 X 句音频已变更，请重跑第 4 步"，绝不硬拼
```

| 视频合成 | `smart-compile-engine.ts`（697 行）：转场×8、Ken Burns 运镜×7、标题样式×8、贴纸 | ✅ 有 |
| 成本估算 | `CostEstimate` 类型 | ✅ 有 |

> 我们直接出 MP4，路线更短；它的 CRAFT/MOTION 文档是"画面审美经验"，值得二期借鉴，
> 但不是打通流程的前置条件。

## 七、实施顺序（建议）

```
第 1 步（纸面）：把 3.2 的步骤表细化成"每步的输入/输出/失败处理/回退点" ← 反复打磨的就在这里
第 2 步（最小闭环）：只做 1→4→5→8 四步（文案 → 配音 → 字幕 → 用一张图合成 60 秒）
        —— 先验证"状态机能驱动这条链"，不追求好看
第 3 步：补第 4.2 成本闸门 + 4.3 单步重试（体验刚需）
第 4 步：补第五节衔接校验（防止假成功）
第 5 步：接第 6 步 AI 分镜 + 第 7 步真生成画面（这步开始花钱，前面都便宜）
第 6 步：加"标准模式入口按钮"（方案卡，像现在的发布卡）
第 7 步（二期）：画面审美（借鉴它的 CRAFT/MOTION）+ MG 动画
```

## 八、明确不做的事

```
✗ 不做"让 AI 读一份 SKILL.md 自己发挥"的路线（用户判断正确：我们的模型达不到，且不可控）
✗ 不装 creator-pipeline 原样（它的依赖是 Python3.12+uv+FFmpeg+Node+MiniMax，环境不通用）
✗ 不碰发布工作流（两套 DRAFT 完全独立；符合"标准/自由文件级隔离"原则）
✗ 不找素材（用户明确：纯生成 —— 第 7 步画面全部由模型生成）
```
