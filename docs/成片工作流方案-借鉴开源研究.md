## 〇、三句话结论

1. **三个开源项目（garden-skills / video-shotcraft / video-talkcraft）的技术栈都是 React 系**
   （Vite+React / Remotion）——**代码不能搬**，但它们沉淀的**设计方法与清单可以直接借鉴**。
2. **最值得抄的不是"主题"，是"流程"**：硬检查点、首镜先确认、分段渲染只重渲变更段、
   唯一真相源、自检协议 —— 这些才是它们"反复打磨"的成果。
3. **我们仍走 FFmpeg 路线**（已在用、无 Node 依赖、打包体积小），
   代价是复杂 MG 动画做不了 → 用**"配方卡"把创意限制在 FFmpeg 能实现的范围**，这反而是纪律。

## 二、它们共同的设计（可直接借鉴，共 10 条）

### 2.1 硬检查点（Checkpoint）—— 不许 AI 一口气冲到成品

```
garden-skills 的工作流：
  Phase1 内容编写（一次产出 script.md + outline.md）
     ▼
  [Checkpoint Plan] ← 必须停：一次对齐 5 件事
      稿子 / outline / 主题 / 素材 / 开发模式
     ▼
  Phase2 网页开发
     · 第 1 章 = 主线程 + 完整版本（强制 anchor）
     ▼
  [硬节点] 用户验收第 1 章 ← ★ 不可跳过
     ▼
  · 第 2~N 章（按选定模式：A 逐章 / B 顺序 / C 并行）
     ▼
  [Checkpoint Audio] ← 必须停：是否合成音频
     ▼
  Phase3 音频 → Phase4 录屏后期
```

**价值**：AI 不会"从原文直接冲到最终代码"（它的原话）。**每花大钱/费大时间之前，先和用户对齐。**

### 2.2 首镜先做先确认（video-talkcraft）★ 最值得抄的流程设计

```
"先搭全合成骨架、其余镜头占位，只做样板镜并用 --seg-audio 出一条有声单镜预览给用户确认，
 确认后再做其余镜头。"
```

**价值**：**避免"从头做到尾才发现风格不对"**。先出一条 8 秒的样板，用户点头了再量产。

### 2.3 分段渲染，只重渲变更段（video-talkcraft）

```
· scripts/render_shots.mjs 按镜头切段并行渲，段内单进程保光栅一致
· 改一个镜头只重渲【该段 ± 邻段】
实测（201 秒竖屏片）：全片首渲 13min→9min；★ 改一个镜头出有声新片：整渲 → 53 秒
```

**价值**：这正是我第一版方案里说的"单步可重试"，人家有实测数据支撑。

### 2.4 唯一真相源（防多处漂移）

```
garden-skills：narrations.ts 是 step 数和音频合成的唯一真相源
  → 章节代码里 if (step === N) 的最大 N+1 必须等于 narrations.length
  → "这保证 5 处地方（script / outline / 章节代码 / chapters.ts / 音频文件）永远不会漂"
```

**价值**：这就是"衔接校验"的另一种实现 —— **不是靠人记，是靠结构强制一致。**

### 2.5 硬性自检协议（产出必须过检才汇报）

```
三个产出（script.md / outline.md / 单章实现）完成 → 必须走【自检 → 修复 → 再汇报】
执行方式按能力降级：① 独立 reviewer agent ② subagent ③ 自己严格逐项核查
★ 铁律："拿到结论后先按 fail 项把产出改完，再向用户汇报。
        直接拿原始结论汇报但不修复 = 违规"
```

**价值**：这正好治我们的老毛病 —— "日志说成功、其实失败"。

### 2.6 逐步揭示（禁一次全展示）

```
"当口播在说『第一是 X、第二是 Y、第三是 Z』时，严禁一个 step 把 X/Y/Z 全部 stagger 上来。
 正确：一项 = 一个 step。讲 X 时 X 亮；讲 Y 时 X 灰化保留作上下文 + Y 亮。
 判断标准：讲者会一个一个念出来吗？会 → 必须逐个揭示。"
```

### 2.7 反 AI 味清单（明确黑名单）

```
✗ 紫粉 / 蓝紫对角渐变背景        ✗ 圆角卡片 + 彩色左边框装饰
✗ 渐变按钮 + 大圆角药丸          ✗ emoji 当图标用
✗ 假数据 / 假 logo / 假"X 万用户"  ✗ 整章 N 步用同一种入场动画
✗ 每步都挂 ken burns / 光晕呼吸 / 持续闪烁
✗ 每屏右下角都挂 mono 角标 / 序号
★ 缺的东西【承认缺】—— 用 placeholder 占位卡（"image · 16:9 描述"），
  "不要用 emoji 凑、不要找无关图凑、不要编数字。没有就承认没有，比 fake 强一百倍"
```

### 2.8 运动系统做减法（video-talkcraft）

```
"每场景只保留【一条极缓推拉相机曲线 + 让位】，idle 微动 / 环境呼吸 / 脉冲全部默认关闭。"
```

**价值**：这是"电影感"和"AI 味"的分水岭 —— **动得少、动得准**。

### 2.9 纯文字镜必配陪衬图（G5 系统）

```
"纯文字镜【必配】一张图标 + 方框 + 箭头的线稿陪衬图，文字不裸放、每句至少一个可见变化；
 缺陪衬行 preflight 报 WARN。"
```

### 2.10 双源：节奏跟口播稿，细节回原文

```
"节奏/顺序/节拍 ← script.md；画面细节/数据/引用/案例 ← article.md
 ★ 如果只用了口播稿 —— 屏幕等于把口播打字打了一遍 —— 那就是 PPT，不是视频"
 → 让【画面信息密度 > 口播信息密度】
```

## 三、技术栈差异：为什么不能照搬

| | 它们 | 我们 |
|---|---|---|
| 渲染 | **Vite+React** / **Remotion**（React 视频框架） | **FFmpeg 滤镜链** |
| 动画自由度 | 任意（React 组件想怎么写就怎么写） | 受限（受滤镜能力约束） |
| 环境依赖 | Node + Vite + 760MB node_modules（含 190MB 无头浏览器） | 内置 python + FFmpeg（已在包里） |
| 交付物 | HTML 演示（需录屏）/ React 渲出的 MP4 | **直接 MP4** |
| 可音画同步 | 词级时间戳（20~40ms） | 我们有【句段级】（每句 duration）✅ 够用 |

**结论**：

```
★ 坚持 FFmpeg —— 理由：已在用、不引入 Node 环境、打包体积可控、直接出 MP4
★ 代价：复杂 MG（粒子/字符雨/3D 变形等）做不了
★ 应对：用【配方卡】把创意限制在 FFmpeg 能做的范围 —— 这是纪律，不是妥协
   （它们那 157 张卡里，很多也就是"位移/缩放/淡入/遮罩/分屏"，FFmpeg 都能做）
```

## 四、我们的落地设计（FFmpeg 版）

### 4.1 配方卡（借鉴 shot recipe cards）

```
一张卡 = 一个 JSON：
  {
    "id": "hero-number-countup",
    "name": "大数字跳动",
    "scene": "讲数据/成果",
    "input": ["number"],                 // 输入类型（决定什么时候能用）
    "ffmpeg": "zoom-in + drawtext 数字逐帧递增",   // 实现方式（FFmpeg 滤镜链）
    "duration": [2, 5],                  // 适用时长区间
    "theme_tokens": ["accent", "font-hero"]  // 用哪些主题变量
  }
★ 先做 20~30 张，覆盖最常用的场景即可（不必凑 157 张）
```

### 4.2 多轨单元（借鉴 video-talkcraft 的 7 类）

```
把成片分解成 7 条轨，各自可单独重渲：
  ① 字幕轨（我们的 SRT → ASS）
  ② 转场轨（xfade × 8 已有）
  ③ 环境轨（背景/幕底，对应它们的 backdrop 12 款）
  ④ 镜头轨（推拉/让位，对应"一条极缓推拉"）
  ⑤ 人像轨（数字人，我们有 digital_human）
  ⑥ 配音轨（ttsQwen3 / 火山 TTS）
  ⑦ 音效轨（SFX —— 我们暂缺，二期）
```

### 4.3 主题（借鉴 garden-skills 的 token 体系）

```
★ 一套主题 = 一个 JSON（25~35 个变量）
   · 调色板：bg / surface / text 阶梯 / accent
   · 字体：中文 / 英文 / 正文 / 等宽
   · 圆角性格、分割线性格、hero 数字风格、阴影、装饰
   · ★ 动效气质 mood（电影感慢 / 弹簧 / 利落 / 安静）—— 不写具体 ms
★ 起步：照着它 23 套里的 6~8 套（挑常用场景）翻译成我们的 JSON
   · 例：商务（warm-keynote）、科技（blueprint / neon-cyber）、
         报刊（newsroom）、极简（monochrome-print）、
         活泼（pastel-dream）、促销（bold-signal）
★ ★ 铁律（抄它的）："一个片子从头到尾只跑一个主题，不在章节间翻明暗"
```

### 4.4 流程（把第一版的 9 步 + 它们的检查点合并）

```
1 起稿            → [Checkpoint Plan] ★ 一次对齐 5 件事
                     （文案 / 分镜大纲 / 主题 / 画面来源 / 生成模式）
2 选音色
3 确认文案
4 分句配音        （句段级时长 = 我们的"真相源"）
5 出字幕 SRT
6 分镜编排        ★ AI 出场
6.5 画面来源      （纯素材 / 纯生成 / 混合补足）
7 ★【首镜先确认】  → 只做 1 个样板镜，出【有声单镜预览】给用户看
                     [硬节点] 用户点头 ← 不可跳过
8 其余镜头生成    （分段渲染，只重渲变更段）
9 合成出片        + 硬性自检（过检才汇报）
10 预览确认
```

### 4.5 唯一真相源（防漂移，抄 garden-skills）

```
我们的"真相源" = 配音产出的 manifest（每句：文本 + 时长 + 音频 hash）
  校验链：分镜表 → 每镜时长必须由 manifest 派生
          SRT     → 必须由 manifest 派生
          合成    → 引用前先校验 hash（不一致就报错，不硬拼）
```

## 五、相对第一版，本方案新增/修正了什么

```
+ 新增【Checkpoint Plan】（一次对齐 5 件事）—— 原来只说"逐步推进"
+ 新增【首镜先确认】—— 原来没有，这是最省的防错机制
+ 新增【分段渲染只重渲变更段】—— 原来只说"单步可重试"，现在有了具体做法和实测数据
+ 新增【唯一真相源 = manifest】—— 原来只说"要校验"，现在指定了校验链
+ 新增【硬性自检协议】—— 产出必须过检才汇报（治"假成功"）
+ 新增【反 AI 味黑名单】—— 直接可用
+ 新增【配方卡 + 主题 JSON】—— 原来抽象，现在有具体结构
+ 修正：多轨单元明确为 7 类
+ 修正：明确"不引入 Node/Remotion"，坚持 FFmpeg
```

```
第 0 步 纸面：把 4.4 的流程表细化到"每步输入/产出/失败处理/回退点"（就这一份，反复打磨）
```
