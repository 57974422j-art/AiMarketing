# HTML 动态 PPT 方案 + 可行性探针结论（2026-10-02）

> 状态：**方向已定、探针已过、母版样板在做**。本文是唯一权威口径，后续页型契约/母版/回填都以此为准。
> 关联：`EXECUTION_LOG.md`（2026-10-02 两条）、`dist-rel/probe-hf/REPORT.md`（探针原始报告与证据帧）。

## 一、为什么要转（用户原始诉求 + 实测证据）

用户原话：「**打字是大字 PPT 还是模版打字**」「我们设定的 PPT 其实**只是一个 PPT 的一页，不是一套风格完整的 PPT**」「**所有 PPT 都是独立镜头**」「**几乎没有动效**，这和我预估的差很多」「本次最大问题还是 **AIPPT 内容不足**」。

**实测尸检（用户 17:21 那条 34 镜片留档 `vf-20261002-172103-u1.json`）**：

| 事实 | 数据 |
|---|---|
| 镜数 | 34 = 20 × `bgimage` + 11 × `title·center` + 3 × `video` |
| 版式 | **`variant` 全空 → 0 页 PPT** |
| 根级 | `style = null`（**没选成品风格**）、`deck_style=auto`、`duration=180`（秒） |
| 内容 | 大字全是「AI营销神器 / AI营销生成系统」这类**名词短语**；`items` 全空、无数据、无图表 |

**两条根因**：
1. 「每 2~3 镜至少一页 PPT」的兜底**只在显式选了成品风格时才生效** → 没选风格 → 0 页 PPT；即便生效，也只是"把某几镜换成某一页"，**仍然不成套**；
2. **AI 从来没被要求产出"一页的内容"，只被要求产出"一句大字"** → 内容不足是**契约问题**，不是模型问题。

**结论（用户判断正确，我也认）**：错在架构。以"镜"为单位、每镜只要一句大字，是天花板。

## 二、目标与产品形态

用户视角只有三步：
1. 给一句标题（或丢素材、或给内容/风格提示词）
2. **看到一整套动态 PPT**（可翻页预览、可换风格）—— 现有"逐镜静帧预览"改为"整套翻页预览"
3. 满意 → 点「确认出片」

**架构四层**（页 = 内容单位，镜 = 时间单位）：

```
① 内容层(AI)      口播文案 + 素材 → deck.json（母版 + 页序列 + 每页完整内容 + 风格）
② 成册渲染(HF)    同一母版 + 同一套动效语言，把每页渲成"动态页"
③ 回填层          按旁白把「页」切进「镜」（一页可拆 2~3 镜；几页可配一段旁白）
④ 出片层          现有 render.py 链路不动（配音/字幕/拼接/编码/混音）
```

## 三、页型契约 v1

**12 种页型**：封面 · 章节页 · 目录 · **要点页** · **数据页** · **图表页** · 对比页 · 引用页 · 图片页 · **步骤页** · 小结页 · 尾页

**实现进度（2026-10-02）**：**已实现 10 种** —— 封面 `cover` · 要点 `bullets` · 数据 `data` · 尾页 `end` + 章节 `section` · 图表 `chart`（`bar`/`line`/`donut`）· 对比 `compare` · 引用 `quote` · 目录 `toc` · 小结 `summary`；**待做 2 种**：图片页、步骤页。**已跑通 8 页 / 24 秒整片**（`cover → section → bullets → chart → compare → data → quote → end`，600 帧，`tv+bt709`），**图表真画且有像素证明**（抽帧量柱高，5 根柱误差 ≤±1px）。
**母版已枚举化 + 已做 2 套皮肤**：`masters/<id>/master.json` 清单化（母版自带的资产根/单页时长/画布/绘图区/素材名/配色表全在清单里，**生成器不再自带任何母版数值**）；`master-v1`（暗色暖金）与 `master-v2`（浅色商务蓝）**同 10 页型**，同一个 deck 只改 `masterId` 各出一条 8 页 24 秒片；**两套像素证明不同**（亮度 Δ0.805 / 主色相 Δ192.9° / 同帧平均差 209.19/255）；**1→1 字节级回归 3 次全 PASS**（`master-v1` 手写片 MD5 恒为 `7F1B528D…`）。

**字段（示例）**
- 公共：`页型 / 页码 / 标题 / （副标）/ 旁白句 / （来源）`
- 要点页：要点 **≥3 条且每条 ≥8 字**（+ 可选图标）
- 数据页：**1 个大数字 + 单位 + 一句解释**（+ 可选对比值 / 2 个次要指标）
- 图表页：**≥4 个数据点 + 图型**（折线/柱/占比）
- 图片页：1 张图 + 一句标题；封面：主标题 + 副标 + 出品方/日期；尾页：主句 + CTA

**内容量下限 = 硬规矩**（不达标不许用该页型）—— 直接治"内容不足"。

**风格参数（AI 只能在这几个里选/调，不许出模板）**：`母版ID / 配色（跟随素材主色或指定）/ 密度（松-中-紧）/ 节奏（快-中-慢）`。

**最小完备集（第一套样板）**：封面 + 要点页 + 数据页 + 尾页。

**契约已实现为"可执行"版本（2026-10-02，已自验）**：`deck.schema.json`（字段 + 内容量下限，**风格五项全是枚举**）· `AI-PROMPT.md`（只许输出该 JSON、禁 HTML/CSS/JS、**不许给数值**、含输出前自检清单与"宁少勿虚"）· `validate-deck.mjs`（零依赖校验器，报"哪页不达标、缺什么"并**给替换页型建议**，另加三条 schema 表达不了的闸门：**首屏必须 cover**、**字符串里出现 HTML/CSS 标记即违规**、**`metric.number` 必须是数字类型**（拿不到真数字就不许用数据页 —— 治"AI 乱编数字"最有效的一条））。样例：`examples/deck.master-v1.json`（**金样例 = 母版事实基准**，exit 0）、`deck.bad.json`（13 不达标 + 3 建议，exit 1）、`deck.html-injected.json`（恰好 3 项，exit 1，**无假阳性**）。↔ 上面探针报告的文本资产副本放在 `docs/ppt-html-probe/`（`dist-rel/` 被 gitignore）。
**一处已确认的"契约三处同步"例外（2026-10-02）**：`palette` 清单是**每母版的数据**（`masters/<id>/master.json`），抄进 JSON Schema 会与母版清单漂移、且跨字段依赖 JSON Schema 表达不了 → 故 `deck.schema.json` 里 `palette` 由 `enum` 降为 **`string + pattern`（只校验形状）**，**权威在校验器**（按所选母版的清单校验，选错会报错并列出该母版可用名）。`masterId` 仍是 schema 里的 `enum`。

## 四、技术选型（已定）

| 路线 | 结论 |
|---|---|
| Remotion | ❌ 公司商用**按用量付费**（Company License / Automators $0.01 per render） |
| 现成开源模板直接套（html-video 20+ / reveal.js / slidev） | ❌ 字段互不相同、AI 无法统一填；多为"网页演示"非"竖屏短视频版式" |
| **HyperFrames（HeyGen，Apache-2.0，0.8.111）** | ✅ **选定**：本地逐帧、无按次费、字节级确定性；我们**自研母版契约**（母版是我们自己的资产） |
| 继续 ffmpeg 手画 | ❌ 已证明到顶（不能真圆角/真模糊/真图表/成套动效） |

**AI 自由度**：终端用户只"选母版 + 调参"；**AI 现场写动画只在造册阶段给内部用**，不进终端。

## 五、探针实测（本机，HyperFrames 0.8.111，非兜底实现）

| 项 | 720p | 1080p | 含义 |
|---|---|---|---|
| 渲染耗时 | 8 秒页 = **12.5s**（62.5ms/帧） | 18.5s（92.3ms/帧） | 34 镜估算：**720p 逐镜起进程 ≈7.1 分钟**；**多页一次渲染 ≈3.2 分钟**；1080p ≈10.5 分钟（对照现有 ffmpeg 线 ≈3.2 分钟） |
| 资源 | CPU 峰值 **2.5 核** / 内存 +0.55GB | 峰值 5 核 / +1.1GB | **4 核 16G：并发建议 2**（内存能塞 4，CPU 是瓶颈） |
| 确定性 | **`--workers 1` 两次渲染 MP4 MD5 完全相同**；多 worker 只有帧内容一致（PSNR 全 `inf`）而 MD5 不同 | 同 | **"字节级可复现"必须限定 `--workers 1`**（已修正，见 §八.9）；好消息：`--workers 1` **还更快**（12 秒母版 8.7s vs 多 worker 13.1s） |
| 拼接 | 与 `render.py` 产物参数一致，`concat -c copy` exit 0（400 帧 15.92s） | 同 | **新老可混用**；HTML 段**无音轨** → 拼后 mux 旁白/BGM/字幕 |

setup（浏览器启动+校准+静态帧去重）约占单次渲染 **50%** → **"多页塞进一次渲染"是主要提速手段**。

## 六、必补三件（不做就"随机出错"）

1. **字体内嵌**：实测请求不存在的字体**静默回退、不报错**（`Microsoft YaHei` 与 `NoSuchFont-QQQ` 渲染结果一致）→ 换机必变、缺 CJK 直接豆腐块。→ **母版 `@font-face` 内嵌开源字体（Noto Sans/Serif SC，OFL）**；**生产禁用外部字体 CDN**。⚠️ 内嵌只用开源字体，**不得内嵌 msyh（授权问题）**。
2. **素材入口统一转码**：`chrome-headless-shell` **不支持 `.mov`/`.avi`/`.ts`/HEVC**，而上传口白名单收这些（`src/app/video-edit/page.tsx:239` = `['.mp4','.mov','.avi']`；另三处 `accept="image/*,video/*"` 会收 iPhone 的 HEVC）→ **HTML 线入口统一转 H.264 + `+faststart` mp4**（同时是 `<video>` 可靠 seek 的前提）。素材**不能用 `file://`**（Chrome 拦截），必须落进项目目录或用本地 http 服务。
   **★色彩标签必须"转换 + 声明"一次做完（2026-10-02 A/B 实测，非推测）**：同素材只差"有没有色彩标签"，经 HTML 线渲染后 —— **无标签**（现状，素材池与 `render.py` 产物都是无标签）：饱和绿 `(0,161,0) → (0,133,0)`，**偏 −17%**；**显式 `bt709 + tv range`**：`(0,159,0) → (1,156,0)`，**偏差基本消除**。机制：素材无标签时浏览器对色矩阵的默认假设与产物声明的 bt709 不一致 → **饱和色明显偏、中性色几乎不变**（所以肉眼看不出、要量才知道）。
   ⚠️ **规格保留"显式转换 + 声明"，但理由改了**（2026-10-02：srv-env 提"`-colorspace` 只声明不转换、直接标 bt709 会变成标错标签" → **probe-html 先做证伪再落地**，YUV 级实测**推翻了这个机制判断**）：造真身 BT.601 的源（`Y=97 ≈ 601 理论 96.7`）→ 只加 `-colorspace bt709` 声明后 **`Y` 变 113 ≈ 709 理论 114.3** → **ffmpeg 确实转了像素**；"只声明"与"显式 `scale=out_color_matrix` + 声明"两条路输出**逐字节相同**。
   → 因此：**主因仍是"有没有标签"**（无标签 → 浏览器按默认矩阵解释 → 饱和色偏 −17%）；**显式转换写法保留是"防御性 / 不依赖 ffmpeg 版本行为"，不是"因为声明不转换"**。另外三条防御理由（零额外代价）：**① 生产服务器是较老的 ffmpeg，版本差异可能改变该行为**（段C 将用真身 601 素材在**实际生产二进制**上量 raw `Y` 实证）② 上游滤镜链可能改变色矩阵状态 ③ 10bit / 其它 pixel format 差异。入口转码照此写：
   ```
   -vf "scale=out_color_matrix=bt709:out_range=tv,format=yuv420p"
   -color_primaries bt709 -color_trc bt709 -colorspace bt709 -color_range tv -movflags +faststart
   ```
   **根治（不是拼接处补救）**：让**两个生产者都写 bt709/tv** —— HTML 线 + 现有 `render.py` 的 H.264 输出；否则 `concat -c copy` **继承首段标签 → 结果依赖段顺序**，是隐藏的不确定性。
   **验收判据**：`ffprobe` 四字段 = bt709/tv **且** 再渲一次后饱和色角落偏移 **≤3**（照 probe-html 的 A/B 口径）。
   ⚠️ **2026-10-02 修正：`ffprobe` 四字段"通过" ≠ "真的转码了"** —— **remux（`-c copy`）产物会假通过**（标签改了、像素没改）。必须**同时**比 **raw YUV** 或浏览器渲染（见 §八.11/12）。
3. **服务器环境**：Node22（隔离 `/opt`，不动系统 node）+ `chrome-headless-shell` + 字体；并**把两条线的 ffmpeg 指到同一个**。

## 七、已定决策（lead 拍板）

| # | 决策 | 理由 |
|---|---|---|
| D1 | 字体优先级：**① @font-face 内嵌 → ② fontconfig 装系统 → ③ Google Fonts 代理（不进生产）** | 连不上 CDN = 静默回退；代理缓存有淘汰策略 = 破坏字节级确定性 |

| D3 | **两条线共用同一个 ffmpeg**（`HYPERFRAMES_FFMPEG_PATH/FFPROBE_PATH` → `/opt/ffmpeg/new/bin/*`） | 从根上掐掉"本机/服务器双版本行为差异"这一类事故（今日 gradients 事故即此类） |

| D13 | **引擎在仓库里的正式家 = `scripts/vf-deck/`（服务端侧，与 `scripts/video-factory/` 并列）；引擎资产（字体子集 woff2 + `gsap.min.js` + `masters/**`）必须**进 git**；**布局必须钉死**（见下） | ① 部署靠 git（`deploy-server.sh`），引擎放在被忽略的 `dist-rel/` 里 = **服务器拿不到**；② "**零联网 + 字节级确定**"要求字体与动画库**随仓库固定**，不能靠 CDN 或 npm 现拉；③ 客户端包不含 `scripts/**`（已核 `package.json` build.files / extraResources）⇒ **不增加客户端体积**；④ **`node_modules`（hyperframes 本体）不进 git** → 留 `/opt`，用 `ENGINE_HF_BIN` 指过去（正好同时满足"部署可达 / 离线确定 / 不增体积"） |

| D11 | **契约双写（schema 给 AI 读 / validator 给机器执行）必须加"样例集回归自检"**：改任一边，跑三个样例即知有没有漏 | 两份规则同一事实，靠"记得同步"必漏；用金样例 + 反例当回归基线是最便宜的保险 |
| D12 | **下一件立项：`deck.json` → 母版页面的生成器**（端到端缺的最后一环）：渲染前先过 validator · 用 v1 母版做 1:1 映射 · **`--workers 1`** · 出 12 秒整片（含页间转场）· 失败要**大声报**不许静默降级 | 现在 deck.json 只能被校验、还不能自动变成成片；这一环做完才真正"AI 出 PPT"端到端 |

## 八、坑清单（母版必须遵守）

1. **★带 `.clip` 的元素会被引擎移出文档流** → 每个 clip 必须自己写 `position:absolute`（否则标题/要点重叠、元素消失）。
2. **★字体静默回退**（见六.1）→ 必须内嵌。
3. **★素材不能 `file://`** → 相对路径/落进项目目录。
4. 无 GPU 掉进 screenshot 慢路径（1.34×）→ 用 headless-shell。
5. 默认**流式编码**（帧不落盘，pipe 给 ffmpeg），比 PNG 序列快且省盘（代价 0.55~1.1GB 内存）。
6. 每次渲染有固定前置开销（CLI ~2s + 浏览器 ~4~7s）→ **不要按帧数线性外推小片**。
7. `<video>` seek：**Windows 本机已验到帧级正确**（3s 组合 3/3、8s 组合 8/8；t=4.90 期望 22~23 读到 23；无整帧洋红/无整帧纯黑）→ **≤±1 帧**。**不可外推到 Linux/无 GPU**（段E 用同一素材包跑对照，素材包需用 v2）。
8. **★色彩标签不一致会让饱和色偏 ~17%**（见 §六.2）：素材/产物无色彩标签时，浏览器与 ffmpeg 对色矩阵的假设不一致；中性色看不出来、饱和色一眼可量。**转码一律显式写 bt709 + tv range**。
9. **★"字节级确定性"只对 `--workers 1` 成立**（2026-10-02 母版复核时发现，**修正了 §五 的原始结论**）：worker 数**决定渲染路径** —— 单 worker → `drawelement` + **流式编码（顺序、可复现）**；多 worker → `screenshot` + 分块并行编码（顺序不定）→ MD5 不同（但逐帧像素 PSNR 全 `inf`）。**推荐生产用 `--workers 1`：既字节级可复现、又更快**（12 秒母版 8.7s vs 13.1s）。证据：`dist-rel/probe-hf/master-v1/determinism/`。
10. **版式要按"底下有没有画面"排，不能只按对称排**：封面"出品方/日期"原排右下、压在高亮素材上读不清 → 移到左下；纹理层 `opacity` 0.28 偏重会看到竖条纹 → 降到 0.16。
11. **★"统一转码"不许只做 remux（`-c copy`）+ 改色彩声明**（2026-10-02 实测，**证实 srv-env 的担心是真实可达状态**）：`ffmpeg -i cs601.mp4 -c copy -colorspace bt709 …` → `ffprobe` 标签变 bt709，但 **raw YUV 与源完全相同（`Y=97`，仍是 601）** → 这就是"**标签与像素不一致**"的文件（`-c copy` 物理上不转换像素）。→ 要么**真再编码**，要么显式 `scale=out_color_matrix=bt709:out_range=tv`。
12. **★判色彩问题要选对量具（probe-html 自我推翻后立的规矩）**：**不能用"角落 RGB 读数"**判标签问题 —— 该错标文件 ffmpeg 解码给出 `(0,161,0)` 而非理论偏移值，RGB 读数在"容器标签与码流标签打架"时会误导。→ **只用 ① raw YUV 对比 ② 浏览器渲染**。
    **机制（2026-10-02 由"推断"升级为"实测事实"）**：MP4 色彩标签有**两份来源** —— 容器 `colr` atom（`ffprobe` 读它）与 **H.264 码流 VUI**。用 `ffmpeg -v trace -i F -c copy -bsf:v trace_headers -f null -` 直接读位流 VUI 证实：

    | 文件 | 容器 `colr`（ffprobe） | 码流 VUI `matrix_coefficients` | 一致? |
    |---|---|---|---|
    | `cs601.mp4`（源） | tv, `smpte170m` | `6 = smpte170m` | ✓ |
    | `remux-declared.mp4`（`-c copy` + 声明 bt709） | tv, **bt709** | `6 = smpte170m` | **✗ 矛盾** |
    | `decl-only.mp4`（**再编码** + 声明 bt709） | tv, `bt709` | `1 = bt709` | ✓ |

    ⇒ **`-c copy` + `-colorspace` 只改容器 atom、码流 VUI 不动** → 两份标签自相矛盾；该文件解码得 `(0,158,1)` 与 **VUI(601)** 一致 ⇒ **实际解码走码流 VUI**（"各解码器优先级"未逐个定证，但由解码结果反证）→ **只有 `ffprobe` 被误导**。这同时给"`concat -c copy` 混拼制造矛盾"与"**再编码才是干净修法**"（重写 SPS/VUI、两边同时变 bt709）补上了机制支撑。
13. **★"契约能过" ≠ "渲染得出来"（这条真的发生了）**：`style.palette/density/tempo` 起初**能过校验但渲染侧完全没消费** —— 正是设计契约时最怕的假通过。→ 规矩：**每个风格参数字段都必须建立"字段 → 渲染变量"的映射，并用像素证明生效**（实例：底部进度线像素 `warm-gold`=(158,128,87) vs `clay`=(146,112,92)）。
14. **★页窗口与元素时间必须共用"唯一真相源"**：`tempo` 会改 `--xover`，而页窗口正是用 xover 算的 → 生成器必须用**同一个值**算 `data-start/data-duration`，否则 clip 窗口与时间轴错位；同理**任何元素落定时间都要由 tempo 反推**（实例：要点页小结原 3.20s 落定、晚于转场起点 2.75s → 观感"话没说完就淡出"，改成 1.98s 后 P2 同版式 PSNR **31.8 → 51.3 dB**）。
15. **★对账判据别用"整片子串比对"**：大数字是**滚筒渲染**（HTML 里根本没有字面量 `82`）、短字符串（`秒` / `4`）会在别处误命中 → 报出**假泄漏**。→ 改成**按文本节点比对** + 数字单独校验"滚筒格数是否编码了正确数字"；**不做 OCR**（避免引入新误差源），画面靠抽帧人眼确认。
16. **★"跨页泄漏"判据也要收窄**（同日实例）：`HTML 逐帧`（对比页标签）嵌在章节副题里、`2026-10`（封面日期）嵌在引用出处里、`01`（章节编号）撞上要点页编号 —— 全是**正常内容**却被判"泄漏"。→ 改为**只认"独立节点恰好相等"**（并跳过 <4 字的值），纯子串命中降级为**"疑似重复（不拦）"**供人看；收窄后**老 deck 仍全 0**（证明是修判据、不是放水）。
17. **★"契约字段生效"要被覆盖到所有几何**：`body.p`（竖屏覆盖）**直接覆盖 `--pad`** → 契约里的 `density` **在竖屏下完全失效**（只有横屏生效）。→ 改 `--pad-base` 基准 + `--pad: var(--pad-base)` 派生。**教训：凡"契约里承诺的参数"，必须在横屏/竖屏各验一次生效，不能只在一种几何下证明。**
18. **★"写死"往往不在样式层，在生成器层（这次的决定性发现）**：做"可换皮肤"时先查 CSS —— `master.css` 逐条核查是 **100% 令牌驱动**（全文只有 `:root` 有字面色）→ 看起来"已经很干净"；但真正的硬编码全在**生成器**：资产根 / 单页时长 / 画布 / 绘图区 / 绘图区上移量 / 素材名 / 配色表 —— **不修这些，"换母版"在结构上不可能**。→ 全部搬进 `masters/<id>/master.json`，生成器只消费、**并用静态扫描确认不再自带任何母版数值**。**教训：做"可换皮肤"要问"哪些数值不在皮肤里"，而不是"皮肤里有没有写死"。**
19. **★验证器阈值不许写死（跨皮肤会全错）**：图表像素验证器原本写死 `R>70` 判"柱色像素" → **在浅色母版上会把所有像素判成柱**。→ 阈值改为 **`0.5 ×（柱色离底色距离）`**，柱色/底色/不透明度由母版清单给出。**决定性证据**：图表绘图区高度 v1=234px、v2=270px，两套**各自** 5 根柱误差都 ≤±1px —— 若几何还写死，"换母版"必然全线失败。
20. **★CSS 自定义属性在"声明它的元素"上就求值完毕（真实踩了两次）**：为让 `density` 生效，把 `--pad` 改成由 `--pad-base` 派生：`:root{--pad-base:84px; --pad:var(--pad-base)}` + `body.p{--pad-base:54px}` → **竖屏 `--pad` 仍是 84px**（`:root` 上的 `--pad` 已算完并继承，子孙改上游变量不会重算下游），表现为**竖屏图表柱高恒定少 30px（= 84−54）**。→ 修法：**谁设上游基准，谁就在同一块里再派生一次下游**；`density` 改为调**增量** `--pad-dense`（`calc(基准 + 增量)`）⇒ 横竖屏都生效（横 96/72、竖 66/42）。**这是坑 17 被踩的第二次** —— 说明"只在一种几何下做回归"会反复出事；修后做了**横竖屏双向字节回归**（手写 16:9 `7F1B528D…` ✓ · 手写 9:16 `B563588C…` ✓ · 生成器 4 页 ✓ · 8 页 ✓）。
21. **★跨皮肤的颜色判据必须沿"真实合成链"推导**：占比环的扇片是叠在 `.ch-donut-track` 上、而不是直接压在底色上 → 判据要写成 `shade×accent over (rule over bg)`，**并让母版申报参与合成的颜色**（`rule` 等）；漏掉一层中间合成层，判据就会**只在某个皮肤上系统性偏**。（本批顺带修了验证器 3 个自身缺陷：扇片边界要按"类变化点"测而非"最长同色段"、边界混色需短段合并、合成链算法。）

**实验纪律（2026-10-02 立，来自 srv-env 抓出的自洽性陷阱）**：任何"机制类"对照实验**必须先有控制读数（锚点）**。案例：为验证"只写色彩声明是否也会转换像素"，造 601 测试源那一步**本身用的就是同一个被测行为**（`-colorspace smpte170m`）—— 若老版 ffmpeg 不转换，源会变成"标签 601、像素 709"，于是读数差异来自**源**而不是**被测项**，整个对照失效。→ 规矩：**造源必须强制转换**（`scale=out_color_matrix=…`）、**先量源读数确认符合预期**，再解释被测项；**没有锚点的对照实验一律视为无效**。
**判据还要选对量具**（同日追加）：判断色彩标签问题**只用 ① raw YUV 对比 ② 浏览器渲染** —— 角落 RGB 读数在"容器标签与码流标签打架"时会给出误导结果（实例见 §八.12）；同理"`ffprobe` 标签正确"**不是**"转码真的发生"的证据（§八.11）。
**沙箱/环境类实验必须先做"负控制"**（同日第二次追加，来自服务器离线测的准备）：要验"无网可跑"，**必须先证明确实没网**（同 `unshare -n` 内 `curl example.com` 必须打印 `NET-BLOCKED` 才允许继续渲染）—— 否则 `unshare` 静默失效时会渲出一条"有网的成功片"却被写成"零联网成立"。**与 C5b（先确认源 `Y≈97`）同源：先证环境成立，再谈结论。** 另：**基线（对照组）必须与实验组共用同一组 env，唯一变量只能是"有没有网"**。

### 用户流程（3 步，与用户原话对齐：「先让 AI 根据内容出 PPT → 再回填到页面 → 做成视频」）

1. **入口**：AGENT 页新增「做 PPT」（或作为"画面来源"里多一个选项）。用户只给**一句标题**（必填）、可选丢素材 / 写内容 / 给风格提示词；

3. **确认后两条路**：**(a)** 只出 PPT 片（引擎现在就能做：8 页 24 秒，无旁白字幕）；**(b)** 接进现有出片链路（回填切镜 → 拼接 → 配音/字幕/混音 → 成片）。

### 回填切镜（页 = 内容单位，镜 = 时间单位）

- **第一代（我建议先做，最小改动、零风险）**：把整段 HTML 片**当成"一段连续画面素材"**，与其它镜 `concat`（**已验证可行**）；旁白/字幕/混音仍由现有链路叠加 → 引擎只需给出"总时长"。

- **失败回落（硬要求）**：HTML 渲染失败/超时 → 该片**自动回落现有 ffmpeg 版式**，并在卡片上**如实提示"本次用了旧版式"**（不许静默）。
