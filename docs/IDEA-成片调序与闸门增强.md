# 构思记录：用户自己调画面顺序 + openfilm 两点待验证

> 记录于 2026-10-22。**尚未开工**，等用户指定窗口后执行。

---

# 一、用户诉求（原话）

> 「有用户费用调整画面顺序，还要显示画面和配音对上。我现在设置都是自动编排的也可以修改，搞的我有点烦了。搞个编辑器给他自己改算了。还是另外搞个画布给他们自己改前后顺序什么。」

拆解成三件事：

1. **用户想自己调画面顺序**（现在自动编排，AI 排的他不满意）
2. **调完之后，画面和配音必须还对得上**（这是最关键的约束）
3. **不要再麻烦我们人工改**（自助化）

---

# 二、关键事实（决定方案成本）

## 2.1 我们是「逐段配音」（audio-first）

出片流程是：

```
每段先 TTS 生成一段 mp3 → 实测音频时长 → 按实测时长决定该段画面时长 → 逐段渲染 → 拼接
```

⇒ **每一段 = 一段画面 + 一段配音，天然绑定**。

⇒ 推论（**整个方案的基础**）：
- **重排镜头时，"画面 + 配音"作为一个整体一起移动** ⇒ **音画永远同步**，不需要重新配音、不需要重新对齐时间轴
- 只有「**单独改某段时长**」才会破坏同步 ⇒ **必须禁止手改时长**

## 2.2 两种调序时机，成本差 100 倍

| 时机 | 要做什么 | 耗时 | 成本 |
|---|---|---|---|
| **A. 出片前**（确认卡上） | 改 `plan.shots` 顺序 ⇒ 渲染一次 | 正常出片耗时（分钟级） | 正常 |
| **B. 出片后**（对成品） | **要求出片时保留分片** ⇒ 重排后 `ffmpeg concat -c copy` | **秒级** | 几乎为 0 |

⇒ **先做 A**（改动最小、立刻解决诉求），**B 作为二期**（更快，但要求出片时多存分片）。

# 三、推荐方案

## P1（建议先做）：确认卡上加「画面顺序」编辑

**位置**：出片确认卡（`vf_local` 的 `vfScriptCard` / HTML成片的 `film_confirm` / 日报的段清单）

**形态（从简到繁，建议选 ②）**：

| 方案 | 形态 | 开发量 | 说明 |
|---|---|---|---|
| ① 列表 + ↑↓ | 每行：缩略图 · 首句字幕 · 时长 · [↑][↓][🚫删除] | **最小** | 手机友好，零拖拽 |
| ② **缩略图网格 + 拖拽** | 每段一个卡片，按住拖动换位；顶部显示总时长 | **小~中** | 最直观，用户一看就懂 |
| ③ 横向时间线 | 按真实时长画宽度，可拖拽裁切 | **大**（剪辑软件量级） | 不建议（我们不需要裁切） |

**建议 ②**（拖拽排序），因为用户的心智就是"这不顺，我想挪到前面去"。

**必做的三件事**：

1. **每段显示"首句字幕"**（让用户知道这一段说的是什么，不是看缩略图猜）
2. **禁止手改时长**（界面上不给入口），只显示"该段 ~3.2 秒"
3. **实时显示总时长**（重排不改总长；但如果删段，总时长会变，要给提示）

**允许的动作（建议只给这三个）**：

| 动作 | 是否允许 | 为什么 |
|---|---|---|
| **换顺序** | ✅ | 核心诉求，音画同步不受影响 |
| **删除某段** | ✅ | 配音一起删，文案少一句，同步不受影响（但总时长变短，要提示） |
| **改某段字幕/大字** | ✅ | 已有能力（分镜清单可逐镜改） |
| **重复某段** | ⚠️ 可不要 | 容易让文案重复，价值低 |
| **手改某段时长** | ❌ **禁止** | **会破坏音画同步**（这是底线） |
| **换某段的图** | ✅ | 已有能力（"换一张"） |

## P2：出片时保留分片 + 秒级重排

**做法**：

1. 渲染时**保留每段分片**：`out/segments/seg_001.mp4` + `seg_001.mp3` + `segments.json`
   ```json
   { "taskId": "...", "totalDur": 32.4,
     "segments": [ { "i": 1, "dur": 3.2, "subtitle": "…", "img": "x.jpg" } ] }
   ```
2. 用户重排后：`ffmpeg -f concat -safe 0 -i list.txt -c copy out.mp4`
   - **`-c copy` = 不重新编码 ⇒ 秒级**
   - 前提：所有分片编码参数一致（同源渲染，天然一致）
3. **需要处理的风险**：
   - 段与段之间的**转场**（如果现在有淡入淡出，concat 会丢失）⇒ 要么保持无转场，要么重排后重新渲染转场那几帧
   - **烧进画面的字幕**：天然跟着走 ✅
   - **单独 srt 字幕**：要重排时间轴（`srt` 重新算累计时长）

**验收**：重排 10 段 ⇒ 从点"重新合成"到出片 **< 10 秒**。

# 四、难点与坑（提前列出）

| # | 坑 | 处理 |
|---|---|---|
| 1 | **用户删段后总时长变短**，可能与"目标时长 30 秒"不符 | 界面显示"实际 27.4 秒"，不强行补；或提供"自动补一段" |
| 2 | **首尾段有特殊语义**（封面 / 结尾 CTA） | 建议**锁定首段不可拖**（或允许但给提示） |
| 3 | **同一张图被多段复用**，重排后可能出现"相邻两段同一张图" | 重排后跑一次"相邻重复检测"，给提示（不强制改） |
| 4 | **重排后 `cover`（字幕覆盖率）不变** | 因为内容没变，只是顺序变 ⇒ 覆盖率校验可以跳过（省时间） |
| 5 | **分片体积** | 保留分片会多占磁盘 ⇒ 设 7 天清理（与现有临时目录策略一致） |
| 6 | **HTML成片 / 日报也有同样诉求** | 三个界面**复用同一个组件**（顺序编辑器），但**数据源不同** ⇒ 组件只吃"统一的段数组" |

# 五、复用的可能性（重要）

三条件片线其实都有"段"的概念：

| 线 | 段在哪 | 能否复用同一个编辑器 |
|---|---|---|
| 图片成片 / 图视混剪 | `plan.shots`（`buildVideoPlan`） | ✅ 改 shots 顺序 |
| HTML 成片 | `spec.scenes`（`film-spec.ts`） | ✅ 改 scenes 顺序 |
| 日报落地页 | `d.plan.segments` | ✅ 改 segments 顺序 |

⇒ **做一个通用组件**：入参 `[{ id, thumb, subtitle, dur }]`，出参"新顺序数组" ⇒ 三条线各自把结果写回自己的数据结构。

# 六、openfilm 两点（用户说"晚点再找窗口验证"）

项目：`github.com/openfilm/openfilm`（MIT · 1.9k stars · TypeScript monorepo · 浏览器渲染 + ffmpeg）

**结论：不接入整条，但抄两点。**

## 待验证 ①：`look` 的双次乱序渲染一致性检查

它的做法：**每一帧用两种乱序各画两遍，比对是否一致**，同时报告页面报错 / 字体加载失败 / 音频缺失 / 文字被裁切。

⇒ 可做成我们自己的**闸门增强**（不引入它的代码）：
- 现在我们是"渲染完看结果"，它是"渲染时自证确定性"
- 我们的 `hyperframes` 已是逐帧 seek，但这个"双次比对"没有

**验证方式**：拿我们现有的一份 plan，写个脚本对同一帧用不同顺序请求两次，比对像素哈希。

## 待验证 ②：`frame(t)` 纯函数契约的文档化

我们的 hyperframes 已经是"逐帧 seek"，但**契约没写成规范**。它的 `SPEC.md` 写清了：`window.film.frame(t)` / `duration` / `ready` / 确定性铁律（同一个 t 必须永远画出同一张图）。

⇒ 照这个格式给我们写一份 `docs/hyperframes-SPEC.md`，对将来"AI 自由页"（第三阶段）是地基。
